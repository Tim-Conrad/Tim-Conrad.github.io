Agents without long-lived secrets, approved from my phone

My agents can read keys that never expire. A design where they hold none: tokens bound to a key, a broker that knows which program asks, a phone that shows what the agent wants to do, and a gateway that keeps the last keys.

SpokenAgents without long-lived secrets, approved from my phone. A thought by Tim Conrad, read aloud. It takes a little over half an hour, in fifteen chapters. Three words carry the idea. A bearer token, which works for anyone who holds a copy. A grant, a short permission that my phone signs. And the gateway, the one place where the last keys live. When a figure comes up, the narration describes it, so you can listen without the screen.

Keys that live for years

My agents run as me. Whatever I can read, they can read. On my machines that includes API keys for the models and for a voice service, deploy keys for the repositories, GitHub and cloud tokens, and the service passwords of my lab. Most of them have no expiry date. They stay valid until someone rotates them, which means: makes a new one and switches the old one off.

An agent does not need to be evil to leak one. It prints an environment variable while it debugs. It pastes a config file into a log. It reads a web page with hidden instructions that tell it to send ~/.config somewhere, which is called a prompt injection. A key that leaks once works for whoever has it, from anywhere, for as long as it lives.

I want to get rid of that kind of secret, at least within reach of an agent. This thought is the design I would build: what exists already, what is missing, and a phone app that approves what an agent may do instead of handing it a key. I call the app Countersign for now.

A secret is something you can copy

First, two terms. An access token is the string that an app sends with each request to show that it may call an API. OAuth is the standard way to hand out such tokens. Most of them are bearer tokens. In the words of the standard, any party in possession of the token can use it, and it does not have to prove that it holds a key [1].

A password and an API key work the same way: whoever shows it, gets in. The server cannot tell the owner from someone with a copy. That is the problem, more than the lifetime. A bearer token is like a cinema ticket. The person at the door looks at the ticket, not at you.

The fix rests on a key pair. A program makes two keys that belong together. The private key stays with the program and can sign data. The public key can be shown to anyone, and it checks that a signature came from the private key. A signature does not give the private key away, so the program can sign as often as it likes.

DPoP, short for Demonstrating Proof of Possession, uses that. RFC 9449, from September 2023, binds an access token to the key pair of the client [3]. When the server issues the token, it writes the thumbprint of the client's public key into it (cnf.jkt). A thumbprint is a short hash that names one key [5]. From then on the token alone is not enough. To return to the cinema: the ticket now names a key, and at every door you sign again.

That signature is the proof. With each request the client sends a fresh one: a small JWT, which is a signed JSON document [2]. It says what this one request is: the HTTP method (htm), the URL (htu), the time (iat), a unique id (jti) and a hash of the token (ath). The server checks the signature against the key that the token names. It can also send a nonce, a random value that the next proof must contain, so nobody can make proofs in advance [4].

a DPoP proof, decoded
header   { "typ": "dpop+jwt", "alg": "ES256", "jwk": { public key of the agent } }
payload  { "htm": "POST",
           "htu": "https://gw.lab/github/repos/Tim-Conrad/sealed/git/refs",
           "iat": 1794826800,
           "jti": "e1j3V_bKic8-LAEB",
           "ath": "fUHyO2r2Z3DZ53EsNrWBb0xWXoaNy59IiKCAqksmQEo" }
signed   with the private key, which never leaves the agent's process

A copied token is now useless without the private key. And a copied proof is useless too: it is good for one method on one URL, for a short time, once.

RFC 8705 does the same with a TLS client certificate [6]. DPoP works at the HTTP layer instead, so it also passes through proxies, and a short-lived program can make a fresh key pair whenever it starts. Keycloak, Spring Security and Okta support DPoP today [7] [8] [9].

So the rule I want: nothing an agent holds may work without a key that cannot be copied. A private key is still a secret. But if it lives only in the memory of one process, or in a TPM or a phone's secure chip, there is nothing to paste into a log.

The design in one picture

DPoP solves the copy. It does not answer who decides that the agent gets a token, for what, and for how long. That is where the phone comes in. The design has five parts, plus the APIs that they protect. Each part does one job and holds as little as it can.

Two things follow from the picture. The phone never sends a secret anywhere: it signs a statement. And the agent never sees an upstream key, because the gateway adds it on the way out. Claude Code's cloud sessions, which I use, already do this second part: I save an API key on the environment, a proxy adds it to requests to that host, and the session never sees the value.

Who is asking

"An agent wants to push" is not enough. Which program? Started by whom? The same request from Claude Code in a session I started, and from an unknown binary in /tmp, must look very different on the phone.

macOS has an answer that I would like to copy. Every app there carries a code signature: the developer signs the program file with a key, and the system checks it. The system identifies an app by that signature, not by its path or name.

The core of it is the designated requirement: a rule, stored with the app, that says which signatures count as the same app. In Apple's words, it is "the code's way of saying 'If you see me again, here's how you tell it's really me'" [10]. For an app from a registered developer, the rule names the developer's Team ID. A new version meets the same rule, so the permissions I gave the app (camera, files, screen) stay with it. A changed binary does not, so they do not [10].

A service on macOS can apply such a rule to the program on the other end of a connection. XPC is how apps and services talk to each other there, and setCodeSigningRequirement makes the system drop an XPC connection whose peer does not meet a requirement [11]. Apple's engineers advise naming the peer by its audit token, a value from the kernel for that exact process, not by its process id [12]. A process id is only a number. After a process ends, the same number can go to another one.

Linux has no single signing system for programs. But it has most of the pieces to build the same check in a broker:

  • The peer of a socket. SO_PEERCRED gives the user and the process id of the program on the other end of a Unix socket. Since Linux 6.5, SO_PEERPIDFD gives a pidfd instead [13]: a file descriptor that refers to one process [14]. Unlike a bare process id, it does not start to point to another process when the number is reused. That is the audit token of Linux.
  • The program. From the pidfd, /proc/<pid>/exe leads to the binary. The broker needs a hash of it that it can trust. fs-verity gives one: the kernel keeps a hash tree for a read-only file and checks every read against it, so the file cannot change under its hash [15]. IMA, the kernel's integrity measurement, hashes files as they are run [13]. SPIRE, a tool that gives identities to workloads, already checks programs this way: it reports the user, the group, the path and the SHA-256 of the binary [16].
  • The context. Each process sits in a cgroup, a group that the kernel keeps for it, and systemd names that group after its unit or scope. So the broker can see "a terminal session of tim" or "the backup timer". Flatpak's portals identify sandboxed apps in a similar way, and use pidfds to do it safely [17].

SpokenIn short: the socket names the process, the hash names the program, and the cgroup says how it was started.

So the broker can write a requirement much like Apple's, only from other parts:

a requirement for the broker, a sketch
requirement claude-code
  exe      = /usr/bin/node
  script   = ~/.local/lib/node_modules/@anthropic-ai/claude-code/cli.js
  script.sha256 in npm-integrity(@anthropic-ai/claude-code)
  uid      = tim
  unit     ~ "session-*.scope"        # started from my login, not a timer
  ptrace   = denied                   # Yama scope 2, or its own user

Two things are harder than on macOS, and the design must be honest about them.

  • Interpreters. Many agents run in Node or Python. The binary is the interpreter, and the program is a script. The broker has to identify the script too, and check its hash against the package it came from. A program that loads more code at run time is only as trustworthy as that code.
  • Same user, same power. On a normal desktop, any process of mine can attach a debugger to another one of my processes, read its memory and change it. The kernel calls this ptrace. Yama, a kernel security module, can limit it to child processes, to the administrator, or switch it off [18]. macOS blocks it for hardened apps. On Linux the broker can only trust an identity if the agent runs as its own user, in a sandbox, or with ptrace restricted. Otherwise the check is only a hint, and the phone must say so.

Show the intent, not a button

The push prompts I know ask "Is this you?" with two buttons. People approve them without reading. Attackers count on it: they send prompt after prompt until someone taps yes, which is called MFA fatigue. Microsoft made number matching mandatory in its Authenticator app in May 2023 for that reason [19]. The login screen shows a number and the person types it into the app, so a prompt they did not cause cannot be approved by reflex. That answers "did I cause this?". It does not say what I agree to.

For that, two kinds of prior art exist. The first kind are screens that sign what they show. Secure Payment Confirmation in the browser must show the payee, the amount and the card, and its signature covers exactly that data [20]. Android's Protected Confirmation shows a short statement in a full-screen dialog, and signs it with a key that can sign nothing else [21].

The second kind are formats for the content. Rich Authorization Requests, RFC 9396, let an OAuth request carry a list called authorization_details. Each entry has a type and the fields that say exactly what is allowed [22]. CIBA, the OpenID flow where one device asks and another one approves, shows the same short binding_message on both [23].

So one half of the answer is a screen that signs what it shows. The other half is a request that says exactly what it wants. Put together, the phone shows a request in six parts, and what it signs is exactly what it shows.

The most important line on that screen is the difference between "the broker checked this" and "the agent says this". An agent that read a poisoned web page can give a perfect reason. It cannot fake the program, the branch or the repository, because the gateway will refuse anything outside the grant.

Grants instead of secrets

What the phone signs I call a grant. It is a short JWT, signed with ES256, a common elliptic-curve signature. The key sits in the phone's StrongBox, a separate secure chip with its own processor and storage. Its key material never leaves the secure hardware, and Android can make each use of the key wait for my fingerprint [24]. A grant names the agent's key, so only that agent can use it:

a grant, decoded
{ "iss": "phone:tim-pixel",
  "sub": "tim",
  "cnf": { "jkt": "0ZcOCORZNYy-DWpqq30jZyJGHTN0d2HglBV3uiguA4I" },   # the agent's key
  "req": { "machine": "lab-1", "requirement": "claude-code",
           "session": "7f3a", "isolated": true },                  # what the broker checked
  "authorization_details": [{
      "type": "git.push",
      "repository": "Tim-Conrad/Tim-Conrad.github.io",
      "ref": "refs/heads/claude/thought-grants",
      "default_branch": false,
      "uses": 1 }],
  "why": "Push the new thought for review.",                       # the agent's words
  "iat": 1794826800, "exp": 1794834000,                            # two hours at most
  "jti": "g_8Qm2" }

Three properties follow from that shape.

  • It is useless when copied. The gateway accepts it only with a DPoP proof from the key in cnf.jkt.
  • It is narrow. The gateway compares each request with authorization_details. A push to main is outside a grant for a branch.
  • It ends by itself. Two hours at most, and earlier when I end it on the phone. There is nothing to rotate.

A grant per request has its own danger. Asking forty times per session would train me to tap without reading, which is the problem I started with. So the screen offers "this session, 2 h": the same session may repeat the same kind of action within the same limits. The phone shows a list of open grants, each with a button to end it.

Others already ask once and then trust for a while. 1Password's SSH agent asks once per application, and I can approve for that app, for a terminal session or for one request [25]. Tailscale's SSH check mode asks again after a period, 12 hours by default [26]. Krypton kept the SSH key on a phone years ago, and it never left the phone [27]. What none of them carry is the intent: they approve a key, not an action.

Agents also start other agents. A subagent gets its own key and a grant that is narrower than its parent's, never wider. The parent can sign that grant itself, as long as it only removes rights. The gateway then sees a chain: phone, agent, subagent. Token Exchange, RFC 8693, already has a claim for that chain: act, the party that acts for the subject [28]. The phone can show the chain when the subagent asks for something new.

A gateway keeps the last keys

Step seven worked because GitHub hands out short tokens. Some services will take only a static API key for years to come. Those keys do not disappear. But they can move to one place that no agent can read, and that place can be strict about who uses them.

That place is an identity-aware proxy: a proxy in front of a service that checks who sends each request before it passes the request on. The idea is old. Google's BeyondCorp moved access decisions from the network edge to such a proxy, which checks the user and the device on every request [30]. CyberArk's Secretless Broker applies the idea to secrets: the broker connects to the database, and the app never gets the password [31].

agentgateway is the same idea built for agents. It is an open-source proxy for the traffic of agents: to language models, to tools and to other agents [32]. Agents reach tools through MCP, the Model Context Protocol, an open protocol that connects language model apps to tools and data [33]. agentgateway came from Solo.io and is now a Linux Foundation project [32]. Three of its features fit this design:

  • It checks JWTs and runs policies in CEL, a small expression language for rules such as authorization checks [34]. So it can check a grant against the phone's public key and compare a request with the grant's fields.
  • Its backendAuth policy adds stored credentials to the upstream request. The agent sends its request without a key, and the key is added on the way out.
  • It can keep a private key and sign a fresh JWT for each upstream request (jwtSign), or do an RFC 8693 token exchange. For services that accept that, there is no static key at all, only a key that signs [32].

I could not find DPoP proof checks in agentgateway. If they are missing, a small check in front of it can do that part. Tailscale's Aperture, in beta, keeps model provider keys in a gateway too, and lets clients in by their Tailscale identity [35].

The upstream keys that remain must be few, listed in one file, and used only by the gateway. Where a service offers a short token from a trusted identity, the gateway uses that instead, and the static key goes away.

SpokenOne piece is still missing. The broker and the phone must trust each other before any of this works.

Pairing the phone

The phone and the broker meet once, in person. The broker shows a QR code with its public key and a one-time code. The phone scans it, and both run a Noise handshake. Noise is a framework for secure channels built on Diffie-Hellman key agreement [36]. In Diffie-Hellman, each side combines its own private key with the other side's public key. Both arrive at the same shared secret, and someone who sees only the public keys cannot compute it.

After the handshake each side knows the other's public key, and every message between them is encrypted end to end. The one-time code from the QR goes into the handshake as a pre-shared key, so a relay in the middle cannot join it [36].

Without a camera, a short code works, as in Magic Wormhole: a few words, typed on the other device. It uses a PAKE, a password-authenticated key exchange, which turns a short code into a strong shared key. An attacker gets one guess per code, and a wrong guess makes the connection fail [37].

The phone's key gets an attestation from Android: a certificate chain to Google's root that says the key was made in StrongBox and cannot leave it [38]. The gateway checks it once, when I add the phone, and then trusts the public key.

Further out

The ideas above I would build. These go further, and some may be bad. Each one pushes the same idea: approve what an agent means to do, not a key.

  • Approve the plan, not each click. At the start of a task the agent sends its plan as a list of authorization_details: push to this branch, open one pull request, call the voice API for at most 40 lines. I approve the plan once, and the gateway refuses anything outside it. When the plan changes, the phone shows the difference, like a diff. The agent also has to say what it is about to do, and a request I can read is a plan I can correct.
  • Receipts. Every request through the gateway produces a signed record. Once a week the phone shows what I approved and what happened. A grant that was never used was too wide.
  • Rules that grow from approvals. After I approve the same request the fifth time, the phone offers a rule: "Claude Code in a session of mine may push to claude/* branches, for 30 days." A rule that is not used for a month expires.
  • Two keys for big actions. A push to main, a deploy, a payment or deleting data needs a second approval, from a second device or a second person, like two keys for a safe.
  • Tripwires. If no real secrets lie around, any secret that does is bait. Put fake API keys where agents look. Any use of one is an alarm, and the gateway knows which session read it.

What these have in common: the more exactly a request says what it wants, the less I have to trust the agent that sends it.

What I would build first

The smallest version that removes a real key from my machines:

  1. The broker. A small daemon with a Unix socket. It reads SO_PEERPIDFD, finds the binary, the script and the systemd unit, and matches requirements from a file. First it only logs, so I can see what my agents actually ask for.
  2. The phone app. Android, a key in StrongBox that needs my fingerprint, pairing by QR code and a Noise handshake, and a relay with push. Templates for three types: git.push, http.call to an API, and secret.use for the old keys.
  3. The gateway. agentgateway on my lab, in front of the GitHub API and the model APIs. It checks the grant as a JWT with the phone's public key, and a small service in front checks the DPoP proof. Pushes go out with a GitHub App's installation token, and the voice service's key moves from ~/.config into the gateway.
  4. One agent. Claude Code on the lab, as its own user, with a git credential helper that asks the broker. Then the deploy keys, one by one.

A good test of the design: after step 4, grep -r for keys in the agent's home finds nothing that works.

What it does not solve

  • A wrong action I approved. If I approve a bad push, the push happens. The design makes the request readable. It cannot make me read it.
  • Approval fatigue. Standing grants and plans reduce the number of questions. Whether I still read the twentieth one, I will only know by trying.
  • A program that pretends. On a desktop where the agent shares my user, another process can change it while it runs. The identity check is only strong for agents in their own user or sandbox.
  • Root, a broken phone, a broken gateway. The broker trusts the kernel. The grant trusts the phone. The upstream keys trust the gateway. Each is one place to protect instead of a hundred, but it is still a place.
  • Losing the phone. A second paired device is the clean answer. A paper recovery key in a drawer is the honest one, and it is a long-lived secret again, only one that no program can reach.
  • Services with static keys. They stay, in the gateway, until they offer something better.

The same pattern runs through sealed, which keeps the keys in the browser where a script cannot export them. A key that cannot be copied is the thing I trust most. Grants and receipts are how I would extend that trust to agents, one narrow, short promise at a time.

Open questions

  • Should the wire format be CIBA, so that an existing identity provider such as Keycloak can be the broker's partner, or is my own small protocol simpler?
  • How do I name and version the request types, so that a template on the phone and a check in the gateway always agree on what a field means?
  • How reliably can a broker identify a script inside Node or Python? Is the package hash enough?
  • Does agentgateway check DPoP proofs, or will it soon?
  • Android's Protected Confirmation would be the right screen for the approval, but it seems to be on its way out. Is a normal screen with a biometric prompt good enough?
  • Is there a way to recover from a lost phone without any long-lived secret at all?
