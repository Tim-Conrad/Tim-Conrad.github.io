Agents without long-lived secrets, approved from my phone

My agents can read keys that never expire. A design where they hold none: tokens bound to a key, a broker that knows which program asks, a phone that shows what the agent wants to do, and a gateway that keeps the last keys.

Keys that live for years

My agents run as me. Whatever I can read, they can read. On my machines that includes API keys for the models and for a voice service, deploy keys for the repositories, GitHub and cloud tokens, and the service passwords of my lab. Most of them have no expiry date. They stay valid until someone rotates them.

An agent does not need to be evil to leak one. It prints an environment variable while it debugs. It pastes a config file into a log. It reads a web page that tells it to send ~/.config somewhere. A key that leaks once works for whoever has it, from anywhere, for as long as it lives.

I want to get rid of that kind of secret, at least within reach of an agent. This thought is the design I would build: what exists already, what is missing, and a phone app that approves what an agent may do instead of handing it a key. I call the app Countersign for now.

A secret is something you can copy

A password, an API key and a bearer token have one thing in common: whoever shows it, gets in. The server cannot tell the owner from someone with a copy. That is the problem, more than the lifetime.

DPoP changes that. RFC 9449, from September 2023, binds an OAuth access token to a key pair of the client [1]. The token names the key by its thumbprint (cnf.jkt). With each request the client sends a fresh, signed proof: a small JWT that contains the HTTP method (htm), the URL (htu), the time (iat), a unique id (jti) and a hash of the token (ath). The server can also send a nonce that the next proof must contain [2].

a DPoP proof, decoded
header   { "typ": "dpop+jwt", "alg": "ES256", "jwk": { public key of the agent } }
payload  { "htm": "POST",
           "htu": "https://gw.lab/github/repos/Tim-Conrad/sealed/git/refs",
           "iat": 1794826800,
           "jti": "e1j3V_bKic8-LAEB",
           "ath": "fUHyO2r2Z3DZ53EsNrWBb0xWXoaNy59IiKCAqksmQEo" }
signed   with the private key, which never leaves the agent's process

A copied token is now useless without the private key. And a copied proof is useless too: it is good for one method on one URL, for a short time, once.

RFC 8705 does the same with a TLS client certificate [3]. DPoP works at the HTTP layer, so it also works through proxies, and a short-lived program can make a fresh key pair whenever it starts. Keycloak supports it fully since 26.4 [4], Spring Security can check DPoP-bound tokens [5], and Okta offers it as an app setting [6].

So the rule I want: nothing an agent holds may work without a key that cannot be copied. A private key is still a secret. But if it lives only in the memory of one process, or in a TPM or a phone's secure element, there is nothing to paste into a log.

The design in one picture

DPoP solves the copy. It does not answer who decides that the agent gets a token, for what, and for how long. That is where the phone comes in. There are five parts. Tap one to read what it does and what it holds.

Two things are worth saying at once. The phone never sends a secret anywhere: it signs a statement. And the agent never sees an upstream key: the gateway adds it on the way out. Claude Code's cloud sessions, which I use, already do the second part: I save an API key on the environment, a proxy adds it to requests to that host, and the session never sees the value.

Who is asking

"An agent wants to push" is not enough. Which program? Started by whom? The same request from Claude Code in a session I started, and from an unknown binary in /tmp, should look very different on the phone.

How macOS knows

On macOS every app carries a code signature, and the system identifies an app by it, not by its path or name. The key idea is the designated requirement: in Apple's words, "the code's way of saying 'If you see me again, here's how you tell it's really me'" [7]. For an app from a registered developer, it names the developer's Team ID in the certificate. A new version of the app meets the same requirement, so the privacy permissions you gave it (camera, files, screen) stay with it. A changed binary does not, so they do not [7].

Two more pieces make it work. Notarization: Apple scans software signed with a Developer ID, and Gatekeeper checks for that ticket [8]. And a service can demand a signature from the process on the other end of its connection: setCodeSigningRequirement drops an XPC connection whose peer does not meet a requirement [9]. Apple's engineers advise identifying the peer by its audit token, not by its process id, because a process id can be reused by another process [10].

What Linux has

Linux has no single signing system for programs. But it has most of the pieces to build the same check in a broker:

  • The peer of a socket. SO_PEERCRED gives the user and process id of the other end of a Unix socket. Since Linux 6.5, SO_PEERPIDFD gives a pidfd instead [11]: a handle to exactly that process, which cannot point to another one if the id is reused. That is the audit token of Linux.
  • The program. From the pidfd, /proc/<pid>/exe leads to the binary. Its hash can come from fs-verity, which the kernel keeps for a file and checks on each read (since 5.4), or from IMA, which measures files as they are run [11]. SPIRE's Unix workload attestor already does this for workloads: it gives the user, the group, the path and the SHA-256 of the binary as selectors [12].
  • The context. The process's cgroup names its systemd unit or scope, so the broker can see "a terminal session of tim" or "the backup timer". Flatpak's portals identify an app by the app id in the sandbox, and use pidfds to do it safely [13].

So the broker can write a requirement much like Apple's, only from other parts:

a requirement for the broker, a sketch
requirement claude-code
  exe      = /usr/bin/node
  script   = ~/.local/lib/node_modules/@anthropic-ai/claude-code/cli.js
  script.sha256 in npm-integrity(@anthropic-ai/claude-code)
  uid      = tim
  unit     ~ "session-*.scope"        # started from my login, not a timer
  ptrace   = denied                   # Yama scope 2, or its own user

Two things are harder than on macOS, and the design must be honest about them.

  • Interpreters. Many agents run in Node or Python. The binary is the interpreter; the program is a script. The broker has to identify the script too, and check its hash against the package it came from. A program that loads more code at run time is only as trustworthy as that code.
  • Same user, same power. On a normal desktop, any process of mine can attach a debugger to another one and change it. macOS blocks that for hardened apps. On Linux the broker can only trust an identity if the agent runs as its own user, in a sandbox, or with ptrace restricted. Otherwise the check is a hint, and the phone should say so.

Show the intent, not a button

The push prompts I know ask "Is this you?" with two buttons. People approve them without reading; attackers count on it and send prompts until someone taps yes. Microsoft made number matching mandatory in its Authenticator app in May 2023 for that reason: the person types a number from the login screen, so a prompt they did not cause cannot be approved by reflex [14]. That fixes "did I cause this". It does not say what I agree to.

There is better prior art for that. Secure Payment Confirmation in the browser must show the payee, the amount and the card, and the signature covers exactly that data [15]. Android's Protected Confirmation shows a message in a screen the app cannot draw over, and signs it with a key that works only for confirmed messages [16]. OAuth has a format for the content: Rich Authorization Requests (RFC 9396) carry a list of authorization_details, each with a type and the fields that say what exactly is allowed [17]. And CIBA, the OpenID flow where one device asks and another one approves, shows a binding_message on both [18].

Put together, the phone shows a request in four parts, and what it signs is exactly what it shows. Tap a part.

The most important line on that screen is the difference between "the broker checked this" and "the agent says this". An agent that read a poisoned web page can give a perfect reason. It cannot fake the program, the branch or the repository, because the gateway will refuse anything outside the grant.

Grants instead of secrets

What the phone signs I call a grant. It is a short JWT, signed with ES256 by the key in the phone's StrongBox chip. Android keeps such a key out of the app's memory, and can bind its use to a fingerprint [19]. A grant names the agent's key, so only that agent can use it:

a grant, decoded
{ "iss": "phone:tim-pixel",
  "sub": "tim",
  "cnf": { "jkt": "0ZcOCORZNYy-DWpqq30jZyJGHTN0d2HglBV3uiguA4I" },   # the agent's key
  "req": { "machine": "lab-1", "requirement": "claude-code",
           "session": "7f3a", "isolated": true },                  # what the broker checked
  "authorization_details": [{
      "type": "git.push",
      "repository": "Tim-Conrad/Tim-Conrad.github.io",
      "ref": "refs/heads/claude/thought-grants",
      "default_branch": false,
      "uses": 1 }],
  "why": "Push the new thought for review.",                       # the agent's words
  "iat": 1794826800, "exp": 1794834000,                            # two hours at most
  "jti": "g_8Qm2" }

Three properties follow from that shape.

  • It is useless when copied. The gateway accepts it only with a DPoP proof from the key in cnf.jkt.
  • It is narrow. The gateway compares each request with authorization_details. A push to main is outside a grant for a branch.
  • It ends by itself. Two hours at most, and earlier when I end it on the phone. There is nothing to rotate.

Standing grants

Asking forty times per session would train me to tap without reading, which is the problem I started with. So the screen offers "this session, 2 h": the same session may repeat the same kind of action within the same limits. The phone shows a list of open grants, each with a button to end it.

1Password's SSH agent already works this way for keys: it asks once per application, and I can approve for that app, for a terminal session or for one request [20]. Tailscale's SSH check mode asks again after a period, 12 hours by default [21]. Krypton did it from a phone years ago: the SSH key lived on the phone and never left it [22]. What none of them carry is the intent: they approve a key, not an action.

Grants for subagents

Agents start other agents. A subagent should get its own key and a grant that is narrower than its parent's, never wider. The parent can sign that grant itself, as long as it only removes rights. The gateway then sees a chain: phone, agent, subagent. Token Exchange (RFC 8693) already has a claim for that chain, act, the party that acts for the subject [23]. The phone can show the chain when the subagent asks for something new.

A gateway keeps the last keys

Some services will take only a static API key for years to come. Those keys do not disappear. But they can move to one place that no agent can read, and that place can be strict about who uses them.

That place is an identity-aware proxy. The idea is old: Google's BeyondCorp moved access decisions from the network edge to a proxy in front of each service, which checks the user and the device on every request [25]. Pomerium is an open-source proxy of that kind [26]. CyberArk's Secretless Broker was built to keep secrets away from client applications: the broker connects to the database, the app does not get the password [27].

agentgateway is the same idea built for agents. It is an open-source proxy for MCP, A2A and LLM traffic, from Solo.io and now a Linux Foundation project [28]. Three of its features fit this design directly [28]:

  • It checks JWTs and runs policies in CEL, so it can verify a grant against the phone's public key and compare a request with its fields.
  • Its backendAuth policy adds stored credentials to the upstream request. The agent sends its request without a key, and the key is added on the way out.
  • It can keep a private key and sign a fresh JWT for each upstream request (jwtSign), or do an RFC 8693 token exchange. For services that accept that, there is no static key at all, only a key that signs.

I could not find DPoP proof checks in agentgateway. If they are missing, a small check in front of it can do that part. Tailscale's Aperture, in beta, keeps model provider keys in a gateway too, and lets clients in by their Tailscale identity [29].

The upstream keys that remain should be few, listed in one file, and used only by the gateway. Where a service offers federation (a GitHub App, a cloud's workload identity), the gateway uses that instead and the static key goes away.

Pairing the phone

The phone and the broker meet once, in person. The broker shows a QR code with its public key and a one-time code. The phone scans it, and both run a Noise handshake: a framework for building secure channels from Diffie-Hellman key exchanges [30]. Afterwards each side knows the other's public key, and every message between them is encrypted end to end. The one-time code from the QR goes into the handshake, so a relay in the middle cannot join it.

Without a camera, a short code works, as in Magic Wormhole: a few words, typed on the other device, run through a PAKE so that a wrong guess fails at once [31].

The phone's key gets an attestation from Android: a certificate chain to Google's root that says the key was made in StrongBox and cannot leave it [32]. The gateway checks it once, when I add the phone, and then trusts the public key.

How long each credential lives

The last bar is the honest part. "No long-lived secrets ever" is not reachable while some services only take static keys. What is reachable: no long-lived secret that an agent can read, and every one that remains in one place, in a list I can see.

Further out

The ideas above I would build. These go further. Some may be bad; I want to think them through anyway.

  • Approve the plan, not each click. At the start of a task the agent sends its plan as a list of authorization_details: push to this branch, open one pull request, call the voice API for at most 40 lines. I approve the plan once. The gateway refuses anything outside it. When the plan changes, the phone shows the difference, like a diff. That is intent in its strongest form: I agree to what the agent means to do before it does it.
  • Receipts. Every request through the gateway produces a signed record. Once a week the phone shows what I approved and what happened. A grant that was never used was too wide.
  • Rules that grow from approvals. After I approve the same request the fifth time, the phone offers a rule: "Claude Code in a session of mine may push to claude/* branches, for 30 days." A rule that is not used for a month expires.
  • Two keys for big actions. A push to main, a deploy, a payment, deleting data: these need a second approval, from a second device or a second person. Like two keys for a safe.
  • Tripwires. If no real secrets lie around, any secret that does is bait. Put fake API keys where agents look. Any use of one is an alarm, and the gateway knows which session read it.
  • Lending access. A friend's agent needs to read one repository. Their broker sends a request to my phone, and I sign a grant for their agent's key: one repository, read only, a week. No account, no token to revoke later.
  • The agent asks better questions. If every request must carry a type, fields and a reason, the agent has to say what it is about to do. That alone may make agents work better on my behalf: a request I can read is also a plan I can correct.

What I would build first

The smallest version that removes a real key from my machines:

  1. The broker. A small daemon with a Unix socket. It reads SO_PEERPIDFD, finds the binary, the script and the systemd unit, and matches requirements from a file. First it only logs, so I can see what my agents actually ask for.
  2. The phone app. Android, a key in StrongBox that needs my fingerprint, pairing by QR code and a Noise handshake, a relay with push. Templates for three types: git.push, http.call to an API, secret.use for the old keys.
  3. The gateway. agentgateway on my lab, in front of the GitHub API and the model APIs. It checks the grant as a JWT with the phone's public key; a small service in front checks the DPoP proof. Pushes go out with a GitHub App's installation token, and the voice service's key moves from ~/.config into the gateway.
  4. One agent. Claude Code on the lab, as its own user, with a git credential helper that asks the broker. Then the deploy keys, one by one.

A good test of the design: after step 4, grep -r for keys in the agent's home finds nothing that works.

What it does not solve

  • A wrong action I approved. If I approve a bad push, the push happens. The design makes the request readable; it cannot make me read it.
  • Approval fatigue. Standing grants and plans reduce the number of questions. Whether I still read the twentieth one, I will only know by trying.
  • A program that pretends. On a desktop where the agent shares my user, another process can change it while it runs. The identity check is only strong for agents in their own user or sandbox.
  • Root, a broken phone, a broken gateway. The broker trusts the kernel. The grant trusts the phone. The upstream keys trust the gateway. Each is one place to protect instead of a hundred, but it is still a place.
  • Losing the phone. A second paired device is the clean answer. A paper recovery key in a drawer is the honest one, and it is a long-lived secret again, only one that no program can reach.
  • Services with static keys. They stay, in the gateway, until they offer something better.

The same pattern runs through sealed, which keeps the keys in the browser where a script cannot export them. A key that cannot be copied is the thing I trust most. Grants and receipts are how I would extend that trust to agents, one narrow, short promise at a time.

Open questions

  • Should the wire format be CIBA, so that an existing identity provider such as Keycloak can be the broker's partner, or is my own small protocol simpler?
  • How do I name and version the request types, so that a template on the phone and a check in the gateway always agree on what a field means?
  • How reliably can a broker identify a script inside Node or Python? Is the package hash enough?
  • Does agentgateway check DPoP proofs, or will it soon?
  • Android's Protected Confirmation would be the right screen for the approval, but it seems to be on its way out. Is a normal screen with a biometric prompt good enough?
  • Is there a way to recover from a lost phone without any long-lived secret at all?

Starting points

  • My own question: can DPoP replace the long-lived passwords, API keys and tokens on my machines, and can a phone approve what my agents may do, over an encrypted link to the Linux machine they run on?
