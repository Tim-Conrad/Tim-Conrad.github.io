A private site on public static hosting

sealed puts a whole static site on a public host in encrypted form. Each reader has their own password, and the browser decrypts every file. How it works, in pictures, and what it does not protect.

Private, without a server

Some things I make are for a few people only. The first one is a pen-and-paper game for friends. I wanted it on my own site, next to everything else, but only for the people I give a password to.

And I wanted to keep the hosting I have: static files on GitHub Pages, with no server of my own that checks passwords. A static host cannot check anything. It hands every file to whoever asks.

So the files themselves have to be locked. sealed is the tool I built for that. It takes a finished static site, encrypts every file, and adds a login page. The host gets ciphertext. The browser of a reader with a password gets the site back, and it works as before [1].

What the host sees

The first question for any design like this: what does the host learn? Switch between the two views.

Besides the blobs, the host serves a login page, a small script, a keyring and a key index. None of them holds a name or a path. That is the whole promise, and it is also the first limit: a picture of 820 KB stays a file of about 820 KB, and anyone can count the readers.

From password to file

Each reader types a name and a password. From those two things alone, the browser finds the right keys. Step through it.

The words, for those who want them: the slow step is PBKDF2 with SHA-256, the split into entry key and id is HKDF, and every file, entry and manifest is sealed with AES-256-GCM. All three come with the browser (WebCrypto). sealed has no other dependency [2].

The worker in the browser

A site is many files: pages, pictures, sound. If each page had to decrypt its own pictures, every app would need to change. sealed puts a service worker in between: a small script that the browser runs beside the page and that answers the page's requests [2].

What the worker does besides that, in plain words [2]:

  • The keys stay put. They are stored in the browser as keys that cannot be exported. A script can ask the browser to use them, but cannot read them out.
  • Sound and video work. A player asks for a file in many small pieces. The worker keeps recently opened files in memory, so it does not decrypt the whole file again for each piece.
  • Offline works. If a site allows it, the worker downloads the files after the login, all but sound and video, and keeps them in the browser's cache, still encrypted.
  • A new version keeps you logged in. On each page load the worker reads the key index again. As long as the reader's keys are still in it, the new files open with the old keys.
  • Logout deletes the keys from the browser.

Names that stay the same

Every blob gets its name from three things: the key of its group, its path and its content. Only someone with the key can work out which name belongs to which path. Without the key, the names look random [2].

The same three things always give the same name. So a file that did not change keeps its name from one version to the next. That has two good effects: a browser that already has it in its cache does not download it again, and on GitHub only the files that really changed show up as changed.

The name is also bound into the encryption of the blob. If the host swapped two blobs, the browser would refuse to decrypt both.

Groups and new keys

A site can have groups: for example one for everything, and one for a chapter that only some readers get. Each file belongs to exactly one group, and each group has its own key. A reader's entry holds the keys of their groups [1]. Switch to see what happens when a reader loses a group.

Why a new key at all? Ben's browser still has the old key of chapter 2. Without a new key, he could keep opening the new files of chapter 2. With it, his old key is not in the key index any more, and his browser forgets it [1].

A new password is different. It changes only the reader's entry, not the group keys. Devices that are logged in stay logged in. To log a reader out everywhere, I take away the access, or make a new key.

On this site

A sealed site can live on its own host, or in a folder below another site. On t7d.dev, sealed sites go below /sealed/, with a login page in the look of this site. Each folder has its own worker, its own key store and its own cache, so several sealed sites can share one address without seeing each other's keys [1].

You can try it: the demo is a small site with a picture, a sound and a bonus page. Log in as reader with the password open-the-demo, or as member with open-the-bonus; only member can open the bonus page. The demo protects nothing: its passwords and keys are public on purpose. A workflow in the sealed repository builds it and publishes it here after each change [1].

The deploy of this site and the publishing of sealed each replace only their own part of the branch that GitHub Pages serves, so they do not overwrite each other. Search engines are asked to stay out of /sealed/.

Compared with StatiCrypt

I am not the first to encrypt static pages. StatiCrypt is the best-known tool: it encrypts an HTML file with a password and returns a page with a password prompt. It also uses AES-256 and 600,000 rounds of PBKDF2, the number OWASP recommends [3] [4]. For one page and one password it is simpler than sealed.

What I needed beyond that:

  • Every file, not only HTML. Pictures, sound and video are encrypted too, and stream through the worker.
  • A password per reader. StatiCrypt has one password per page; its README suggests a workaround for several users [3]. In sealed each reader has their own, and I can take one away without changing the others.
  • Groups. Different readers can open different parts of one site.
  • No changes to the app. The site is built as a normal static site, and the worker makes it work behind the login, offline too.

The price is more moving parts: a build, a worker, and an admin page that keeps the keys.

What it does not protect

These are the limits I know of. They are in the README, and they belong here too [1].

  • Guessing passwords offline. The keyring is public. Anyone can copy it and try passwords on their own computer, as fast as their hardware allows. The slow step makes each try expensive, but only a long password makes guessing hopeless. That is why sealed generates the passwords.
  • Old keyrings stay in the history. On GitHub Pages the published files are in a public repository, with all of their history. After a password change, the old keyring is still there, and so is everything it opens.
  • A reader can copy what they opened. Once a file is decrypted in a browser, it can be saved. A new key protects the next version only.
  • Permissions work per file. If one file holds the content of all groups, every reader who gets that file can read all of it. The site has to be split into files along the groups.
  • Sizes and counts show. The number of files, their sizes, the number of readers and the number of groups are visible.
  • Static sites only. An app with its own server needs something else. And the app cannot bring its own service worker, because sealed's worker takes that place.
  • A delay on GitHub Pages. It caches files for up to ten minutes, so a new password or a new group can take that long to work there.
