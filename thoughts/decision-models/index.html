Amazon replaced Claude Sonnet 4.6 with a small model that only picks from a list. What that kind of model is, where the saving comes from, and when the same move fits security work.

One model for everything

I use whatever model the session runs, and that is a frontier model, for everything. I rarely think about what one call costs. A large model that writes a paragraph of reasoning before it picks one word from a list of twenty is the same model that refactors a codebase.

A post from the Strands Agents team made me stop on that. Two Amazon engineers replaced Claude Sonnet 4.6 with a small decision model in a ticketing system, at a fraction of the cost [1]. My question is how this applies to my own field, security work: at what point should I think about a specialised model, and how would I try one in practice?

What Amazon did

The post is by Carr Onstott, Mehul Jaiswal and the Strands Agents team, from 9 November 2026 [1]. In short:

  • The job: put each ticket of a large internal ticketing system into one of 20 categories. Tickets are customer escalations, capacity requests, automated alarms, security findings and more.
  • Before: Sonnet 4.6 with a long system prompt, writing JSON and reasoning for every ticket.
  • After: Strands Decider, built on Gemma 4 E4B, on a SageMaker instance with one A10G GPU. They first tried the 2B model; the E4B did clearly better on their test set.
  • They rewrote the 20 label descriptions as one- or two-sentence criteria, added a "none" option, and tuned how confident the model must be before a label is applied.
  • Results per ticket: 6,724 tokens became 2,010; the average call took 897 ms instead of 4,215 ms; the cost fell from $0.0222 to about $0.0005 at list prices. They call it 98% less, and "millions of dollars" a year.

They are clear about the limits. It worked because the task is "a closed choice from a known catalog, the volume is high, and the latency of the old path mattered." If the labels need explanation text, the catalog changes weekly, or the context does not fit into a few thousand tokens, "a decision model probably can't replace the LLM's job" [1].

A model that only picks

A decision model does not write text. It gets a state and a question with options, and returns a probability for each option and a confidence [1]. The repository describes it as a model between an LLM and a classic classifier: more general than a classifier, and faster than an LLM [2]. It answers three kinds of question: pick one option, yes or no, and a rating on a scale.

The part I find most useful is the confidence. The repository says that on short classification tasks the model has never seen, answers with a confidence of 0.9 or more are right about 95% of the time; below that, "confirm or ask a person" [2]. Its own evaluation adds a limit: on unseen tasks, picking an option is useful behind such a gate, rating on a scale is not [3]. That gives a clean split: the model handles the clear cases, and the unclear ones go to a person or to the large model.

The repository is under Apache 2.0, and the models are open, from 2B to 26B parameters. The README says they can serve on a CPU [2]. So I can try one on my own machine, without sending anything to a provider.

Where the 98% comes from

The tokens per ticket fell by 70%, not 98%. The output went from 170 tokens to 1, and the prompt got shorter. Most of the saving comes from a change in what is paid for: Sonnet is paid per token, the decision model per instance-hour, $1.408 at list price [1].

An instance costs the same whether it is busy or idle. Amazon says one instance can handle about 5,600 tickets an hour, $250 per million tickets at full use, and about $500 with headroom for bursts [1]. At their volume that is cheap. At mine it may not be.

My own sum, from the post's numbers: one instance-hour costs as much as about 63 Sonnet tickets ($1.408 ÷ $0.0222). Below about 63 tickets an hour, or about 46,000 a month, an instance that runs all the time costs more than calling Sonnet. That leaves out the engineering time, and the cheaper ways to run the model: on a CPU, on hardware I already have, or with an endpoint that scales to zero.

So the real lesson for a small setup is not the price. It is speed, keeping the data in house, and a confidence I can act on.

What the post leaves out

  • No accuracy figure. The post says the E4B was "beating production Sonnet" on a separate set of tickets, and "performed just as well". It gives no number, no count of disagreements, and does not say how each disagreement was judged, or by whom.
  • Two latencies. One request took about 640 ms; the average call took 897 ms. The second probably includes the network and queueing, but the post does not say.
  • A vendor post. It is written by the team that makes the model, on its own site, and ends with a link to the repository. That does not make it wrong. It means I want my own numbers before I believe "just as well".

One detail I trust more because it does not sell anything: the order of the keys in the JSON input changed the answer. The same content with keys in a different order moved the probabilities by up to 0.19. They now sort the keys on every request [1].

Security work has the same shape

Much of security work is the same task as Amazon's: a closed choice from a known list, many times a day. For example:

  • Scanner findings: real, false positive, or needs a person.
  • Alerts: which team, and how urgent.
  • Incoming vulnerability reports: which type from a fixed list, and is it a duplicate of a known report.
  • Dependency updates: does this change touch code we run, yes or no.

Two things are different from ticket labels.

First, the data. Findings, alerts and reports are often exactly what should not leave the house. A small open model on my own hardware keeps them there. For many teams that matters more than the cost.

Second, the input is written by someone who may be an attacker. A report or a log line can carry text meant to steer the model. A decision model cannot write text or call tools, so the worst an injected instruction can do is move the label. That is still bad when the label decides that a finding is ignored. So the threshold should lean one way: when the model is unsure, the item goes to a person, and "dismiss" needs a higher confidence than "look at this".

How I would try it

These steps are my reading of what Amazon did, put in order for a small setup. I have not done them yet.

  1. Find one decision. One question with a fixed list of answers that an LLM or a person answers many times. Not a task that needs text.
  2. Write the list down. Each answer as one or two sentences that say when it applies. Add "none". This is useful even if no model ever reads it.
  3. Collect a test set. A few hundred real items with the answer I checked myself. Take them from the logs of the current way, not from memory.
  4. Try the small model locally. Install it, ask the question on the test set, and count how often it agrees with my answers at each confidence.
  5. Pick the threshold. Above it, the label is applied. Below it, the item goes to a person or to the large model. Set it per answer when one mistake costs more than another.
  6. Run both on real traffic. The old way decides, the new model only answers, and every disagreement gets read. Amazon calls this switch the part they would copy "regardless of model" [1].
  7. Switch with a setting. Keep the way back one change away. Amazon's took 45 seconds [1].
  8. Keep the input the same. Sort the keys, fix the format, and test again when the list of answers changes.

When to think about a specialised model

My checklist, for now. The more of these are true, the more a decision model is worth a try:

  • The answer is one item from a fixed list, a yes or no, or a rating. Nobody reads the reasoning.
  • The list changes rarely, not every week.
  • What the model needs to see fits into a few thousand tokens.
  • The same question comes up often: hundreds of times a day, not ten.
  • Speed matters, or the data should not leave the house.
  • I can say what each mistake costs, and route the unsure cases to a person.
  • I can run the old and the new way side by side before I switch.

If only the first one is true, the frontier model stays. It is the default for a reason: it is the right tool for the tasks that are not a list.

Open questions

  • How did Amazon judge the disagreements between Sonnet and the decision model, and how many were there?
  • How well does a 2B model do on German text, and on the jargon of security findings?
  • How easy is it to move the label with text written into a report or a log line? That needs a test of its own.
  • Below what volume is a CPU on my own hardware good enough, and how long does a call take there?
